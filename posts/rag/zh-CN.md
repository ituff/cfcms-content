**——RAG、LLM Wiki 与 Ontology 如何组成新一代企业知识平台**

当我们讨论企业知识平台时，就会有人提到RAG、LLM Wiki 与 Ontology，但是很多人并不清楚这三者的区别。有人把它们当成三种互相竞争的知识库方案，有人认为有了知识图谱就不再需要检索，也有人期待把文档交给大模型后，企业知识就能自动整理、自动更新、自动变得可信。

这些期待背后，实际上是三个不同的问题：面对当前问题，如何找到可靠证据？面对不断增长的资料，如何把理解成果沉淀下来？面对不同部门和系统，如何让同一个概念始终表达同一个含义？

# 一、为什么只有 RAG 还不够

传统 RAG（Retrieval-Augmented Generation，检索增强生成）解决的是一个直接问题：**如何让大模型在回答前，先查阅企业自己的最新资料，而不只依赖模型参数中的静态知识。**

其典型流程是：文档清洗与分块、生成向量并建立索引；收到问题后进行语义或混合检索；把相关片段作为上下文注入提示词；最后由 LLM 生成回答。AWS 和 Microsoft 的参考架构都把这一过程概括为“摄入—检索—上下文增强—生成”，并强调分块、元数据、嵌入、搜索和端到端评估的重要性。

RAG 的价值十分明确：

- **知识更新快**：替换或重新索引外部资料即可，无需重新训练基础模型；
- **适合非结构化信息**：能覆盖政策、合同、产品手册、报告和会议材料；
- **增强可追溯性**：检索结果可以随回答展示，便于用户核查；
- **降低模型闭门作答的风险**：原始 RAG 研究正是为了把参数化模型与可更新、可检查的外部记忆结合起来。

但 RAG 本质上仍是一种**查询时取证机制**，而不是完整的知识管理体系。

传统 top-k 向量检索擅长找到“与问题相似的片段”，却不天然理解“客户—合同—产品—政策—项目”之间的确定关系，也难以判断两个名称是否指向同一实体。对于跨文档、多跳关系或全局性问题，仅返回少量相似片段可能遗漏关键证据。Microsoft GraphRAG 的研究明确指出，基线 RAG 在连接分散事实以及理解大型语料的整体主题时存在不足。这也是**为什么仅有 RAG 不够**：它能够找到材料，却不会自动形成稳定、统一、持续演进的企业知识结构。

# 二、RAG、LLM Wiki 与 Ontology，各自解决什么问题

## 1. 传统 RAG：把正确证据带到当前问题中

RAG 的基本知识单元通常是**文档片段及其元数据**。它按照关键词、向量相似度或混合搜索寻找相关内容，再由模型临时组织答案。

它最适合：

- 政策、制度、技术文档问答；
- 客服与员工自助；
- 对最新材料进行摘要、比较和解释；
- 需要引用原文的事实型查询。

RAG 并不等于只有向量数据库。生产级方案通常还需要连接器、解析与分块、排序器、权限控制、护栏、编排、反馈和评估体系。因此，**检索结果可解释，不代表整个生成过程天然可解释；索引可更新，也不代表实体、术语和冲突已经被治理。**

## 2. LLM Wiki：把一次性回答变成可复用知识资产

“LLM Wiki”目前更适合被视为一种**新兴设计模式**，而不是已经形成统一标准或产品类别的行业术语。较有代表性的一手定义来自 Andrej Karpathy 发布的“idea file”：它明确把 LLM Wiki 描述为一种利用 LLM 构建知识库的模式，而且刻意保持抽象，不规定具体产品、目录、页面格式或技术实现。

其核心思想是：**不要让模型每次都从原始文档重新发现知识，而是在资料进入系统时，由 LLM 增量维护一套持久、相互链接的知识页面。**

典型能力包括：

- 自动产生实体页、主题页、来源摘要和对比页；
- 维护交叉链接、索引和变更日志；
- 新资料进入时更新已有页面，而不是只增加一个新文档；
- 标记矛盾、过期结论和待人工确认事项；
- 将有价值的问答、分析和决策重新沉淀为页面；
- 同时服务员工阅读和 Agent 获取长期上下文。

因此，LLM Wiki 的价值不在“另一种搜索界面”，而在于把**查询时的临时合成**变成**可阅读、可编辑、可重用、可持续积累的派生知识层**。

但企业不能把自动生成页面直接视为事实源。LLM Wiki 应保留来源、版本、状态和审核记录；原始材料仍应是最终证据。否则，错误摘要也可能随页面更新而被放大。

## 3. Ontology：让不同系统对“同一件事”表达同一含义

Ontology（本体）定义的是一个领域中的：

- **概念与类别**，如客户、产品、合同、项目、政策；
- **实体实例**，如某个具体客户或产品；
- **属性与关系**，如“客户购买产品”“项目依赖系统”；
- **层级、等价、互斥和关系规则**；
- **统一词汇及其正式含义**。

W3C 的 OWL 2 标准将 Ontology 表述为具有形式语义的知识表示：它包含类别、属性、个体和数据值，可以通过推理检查一致性或把隐含知识显式化。

这与向量检索有根本差别：

- 向量检索回答“哪些文本在语义上相似”；
- Ontology 回答“这些对象是什么、如何关联、哪些关系有效”；
- 文档库保存证据；
- 知识图谱则通常保存按照某种语义模型组织的实体和事实。

还要注意一个重要边界：OWL 主要描述意义和逻辑推理，并不等同于数据库式的必填字段校验。OWL 采用开放世界假设，信息缺失不一定代表错误；如果企业需要校验字段、数据类型、基数和允许值，可使用 W3C SHACL 对 RDF 图执行约束验证。

# 三、核心对比：三者为何互补

| \*\*维度\*\* | \*\*传统 RAG\*\* | \*\*LLM Wiki\*\* | \*\*Ontology\*\* |
| --- | --- | --- | --- |
| \*\*核心知识单元\*\* | 文档、片段、元数据 | 页面、摘要、实体页、主题页、交叉链接 | 概念、实体、属性、关系、公理与约束 |
| \*\*主要组织方式\*\* | 文档库与搜索索引 | 人和 Agent 可读的持续演进页面 | 明确的语义模型和关系网络 |
| \*\*查询方式\*\* | 相似性、关键词、混合检索 | 页面导航、搜索、链接遍历与综合 | 图查询、实体匹配、关系路径与逻辑推理 |
| \*\*更新机制\*\* | 更新文档与索引 | 增量重写页面、处理冲突与版本 | 受控修改词汇、映射、规则和事实 |
| \*\*擅长问题\*\* | “原文怎么说？” | “我们现在对这个主题知道什么？” | “这些对象是什么关系、是否一致？” |
| \*\*治理能力\*\* | 依赖外围权限、索引和护栏 | 依赖版本、审核、来源与发布流程 | 可提供统一术语、实体身份、规则和验证 |
| \*\*可解释性\*\* | 可展示检索片段，但生成仍需验证 | 页面和变更过程可读 | 可展示实体、关系、规则和推理路径 |
| \*\*主要局限\*\* | 碎片化、多跳与全局理解较弱 | 自动生成内容可能失真或过期 | 建模和维护成本较高，不适合替代全文证据 |

# 四、组合架构：取证层、知识层与语义治理层

更准确的组合方式不是把三者简单上下堆叠，而是让它们分别承担不同职责：

1. **RAG 是运行时取证层**  
   面向当前问题，从原始资料、Wiki 页面和图谱中选择上下文，并生成带来源的回答。
2. **LLM Wiki 是持久知识呈现层**  
   把来源、历史问答和跨文档综合结果整理为可阅读、可链接、可更新的页面，供员工和 Agent 重复使用。
3. **Ontology 是横向语义与治理层**  
   统一实体身份、业务词汇、关系类型、分类体系和约束，同时服务于文档标注、Wiki 页面组织、查询扩展、知识图谱校验和权限策略。

这一分层与当前实践是相符的：Microsoft GraphRAG 会从文本抽取实体和关系、构建层次化社区并生成摘要；Google Cloud 的参考架构也把向量搜索与知识图谱查询相结合，以取得更互联的上下文。但要避免一个误区：自动抽取的图不一定就是受治理的企业 Ontology。GraphRAG 可以产生查询所需的图结构，而正式 Ontology 还需要领域定义、实体消歧、版本管理、约束以及业务责任人。

下图体现的关键不是“三层技术栈”，而是一个闭环：原始证据进入检索和知识整理流程，Ontology 横向约束两者，员工与 Agent 的查询和反馈再推动 Wiki、图谱与索引持续更新。

# 五、一个通用企业案例：员工询问客户、产品与政策影响

假设员工提问：

“客户 A 使用的是哪些产品？最新服务政策是否适用？哪些进行中的项目可能受到影响？”

**系统如何协同工作**

![图 2  本文建议的协同架构。Ontology 与治理是两条不同的横向支撑能力；图中的“可信”是建设目标，而非技术自动保证。](https://statics.msone.top/assets/posts/01M4JG9RFM6ZF0KXY61KY08QAH/21cd746ccb572925861849f7867804d271886a6801da05ff5de6ccf5b1b44773.png)

图2 Ontology 与治理是两条不同的横向支撑能力。

**第一步：Ontology 解析业务含义。**  
系统识别“客户 A”为客户实体，把产品名称、历史别名和产品系列映射到统一标识；同时知道“适用于”“购买”“部署于”“项目依赖”等是不同关系，而不是简单的相似文本。

**第二步：RAG 查找证据。**  
系统分别检索客户记录、合同、产品资料、政策正文和项目文档。Ontology 提供的实体和关系可用于查询扩展及结果过滤；RAG 则负责返回具体条款、日期、适用范围和来源。

**第三步：LLM Wiki 提供已沉淀的上下文。**  
系统读取客户页、产品页、政策页和项目页中已审核的摘要、关联关系、已知冲突及最近变更，避免每次都从所有原始文件重新综合。

**第四步：生成可核查回答。**  
答案区分“原文明确说明”“根据关系推导”“仍需确认”三类内容，并链接到对应文档片段、实体页和政策页。

**第五步：形成闭环。**  
如果本次查询发现新关联或政策变更，可提出 Wiki 页面更新和图谱关系变更；通过规则校验和人工复核后发布。下次再问相关问题时，系统既能重新取证，也能复用已经沉淀的知识。

# 六、渐进式落地，而不是一次性“大建本体”

![图 3  知识经营的维护闭环。自动化可以提出更新，校验与审核负责把关；图中的价值表述为目标，不是已验证的效果数据。](https://statics.msone.top/assets/posts/01M4JG9RFM6ZF0KXY61KY08QAH/8ad3cc2ebee3ac2cb0d94f62511e8ec5efcb2ab6a3b8ae798363425faf0650c3.png)

图3 知识经营的维护闭环。自动化可以提出更新，校验与审核负责把关

**阶段一：先把 RAG 做可靠**

从高价值、边界清晰的知识域开始，例如政策或产品支持。优先建设：

- 权威来源与版本控制；
- 文档级和片段级权限；
- 混合检索、重排序与引用；
- 检索质量和答案忠实度评估；
- 未找到证据时明确拒答。

**阶段二：把高频问答沉淀为 Wiki**

优先建立少量可复用页面类型：客户、产品、政策、项目、决策和主题摘要。所有页面都应包含来源、最后更新时间、审核状态和责任人。**自动生成，受控发布**，比完全自动写入更适合企业场景。

**阶段三：从最小 Ontology 开始**

不要先追求覆盖全公司的“大而全”模型。先统一最关键的十几个概念、实体标识和关系，例如客户、产品、合同、项目、政策及其主要关系。只有在业务需要时，再增加规则、推理和 SHACL 数据质量约束。

**阶段四：建立双向闭环**

让 Ontology 提高实体检索和查询扩展质量；让 RAG 为 Wiki 更新提供原始证据；让 Wiki 成为员工与 Agent 的稳定知识界面；让反馈、冲突和低置信结果进入人工治理队列。

# 写在最后

企业知识平台的升级，不是把聊天窗口换成 Wiki，也不是把向量数据库换成图数据库。真正的变化，是把知识从一次问答的临时上下文，转化为能够持续维护的组织资产。

RAG 让回答有证据可查；LLM Wiki 让理解成果有地方保存；Ontology 让不同资料与系统拥有共同语言。原始来源、身份授权、版本管理、审核和评估，则决定这些能力能否真正可靠地协同。

所谓“经营知识”，就是同时管理知识的来源、质量、时效、复用与责任。不是让系统越写越多，而是让值得信任的知识越积越深，让已经失效的知识能够退出，让员工和 Agent 每次使用时都知道：哪些是事实，哪些是推导，哪些还需要确认。
